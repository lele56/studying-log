# Skill 基础

## 📅 学习信息
- **日期**: 2026-09-04
- **主题**: Skill 基础
- **目标**: 理解 Agent Skills 的核心定位：把可复用提示词、流程、资源和脚本封装成能力包。

## 📚 核心知识点

### 1. Skill 的核心定位
- Skill 是"可复用的能力包"，把反复出现的经验、提示词模板、参考资料和执行脚本打包成独立目录。与把一切塞进主 Prompt 不同，Skill 让 Agent 按需加载，避免上下文爆炸，同时便于跨项目、跨 Agent 共享。

### 2. SKILL.md 文件结构
- 每个 Skill 必须包含 `SKILL.md`，通常包含：名称、描述（description）、触发条件、正文（instructions）、可选资源引用（resources）和可选脚本（scripts）。描述决定了模型何时会加载该 Skill。

### 3. 渐进式加载机制（Progressive Loading）
- Agent 不会一次性读取所有 Skill 的完整内容，而是分三步：① 只看名称和描述，判断是否匹配当前任务；② 匹配后读取完整 SKILL.md 正文；③ 真正需要时才加载资源文件或执行脚本。这样既节省 Token，又保证能力按需激活。

### 4. Skill 与 Tool / Subagent 的边界
- **Skill**：可复用的方法、资料、提示词模板，本质是"知识包"。
- **Tool**：可执行的动作（API 调用、函数执行），本质是"动作接口"。
- **Subagent**：有独立职责的执行角色，本质是"另一个智能体"。
- 写 Skill 不等于增加新智能体，也不等于让模型获得新 API，而是给它一套"怎么做"的指南。

### 5. 关键概念
- **Skill（技能包）**：一个独立目录，包含 SKILL.md 和可选的资源/脚本。Agent 在任务匹配时按需加载。
- **SKILL.md**：Skill 的核心描述文件，定义名称、描述、触发条件、执行步骤和依赖资源。
- **渐进式加载（Progressive Loading）**：Agent 先看名称和描述，匹配后再读完整文件，需要时才加载资源或运行脚本。避免一次性消耗大量上下文。
- **触发条件（Trigger）**：写在 description 中，告诉模型"什么情况下应该用这个 Skill"。描述太泛会误触发，太窄会该用时不触发。
- **Skill 目录结构**：通常包含 `SKILL.md`（必须）、`resources/`（参考资料）、`scripts/`（可执行脚本），结构清晰便于维护。

### 6. 重要机制
- **名称 + 描述匹配**：Agent 首先扫描所有已注册 Skill 的名称和 description，与当前任务语义匹配，决定是否加载。
- **完整 SKILL.md 读取**：匹配成功后，Agent 读取完整的 SKILL.md 正文，获取详细的执行步骤、格式要求和注意事项。
- **资源文件加载**：当 Skill 正文引用了外部文件（如模板、配置、参考文档）时，Agent 按需读取，不引用则不加载。
- **脚本执行**：部分 Skill 会附带可执行脚本（如 Python、Shell），Agent 在需要时运行脚本获取动态数据或执行操作。

## 💻 示例

### 示例 1：SKILL.md 基础结构
```markdown
---
name: code-review
description: >
  用于代码审查的 Skill。当用户要求审查代码、检查代码质量、
  查找潜在 bug 或给出改进建议时使用。不要用于代码生成或重构。
---

# Code Review Skill

## 审查范围
- 仅审查用户提供的文件或代码片段
- 重点关注：安全性、性能、可读性、边界条件

## 输出格式
按以下模板输出：
1. 问题列表（按严重程度排序）
2. 改进建议
3. 总体评价（优秀/良好/需改进）

## 注意事项
- 不要修改原代码，只给出建议
- 对于风格问题，标注为"建议"而非"错误"
- 如果代码没有明显问题，直接说明"代码质量良好"
```

### 示例 2：Skill 触发流程示意
```
用户输入: "帮我审查一下这个 Python 文件的代码质量"
         ↓
Agent 扫描所有已注册 Skill 的名称和 description
         ↓
匹配到 "code-review" Skill（description 包含"代码审查"）
         ↓
读取完整的 SKILL.md 文件
         ↓
按照 SKILL.md 中的 instructions 执行审查
         ↓
（如果需要）加载 resources/ 中的审查清单模板
         ↓
输出审查结果
```

### 示例 3：Skill 与 Tool 对比
**同一个任务：获取天气信息**

| 方式 | 实现 | 特点 |
|------|------|------|
| **Tool** | 定义 `get_weather(city)` 函数，调用天气 API | 实时获取数据，每次调用都执行动作 |
| **Skill** | 编写 SKILL.md，包含天气查询的步骤、API 文档链接、输出格式模板 | 提供"怎么做"的指南，Agent 按步骤自行操作 |

- **Tool** 适合"直接执行"的场景（API 调用、数据库查询）
- **Skill** 适合"需要指导"的场景（复杂流程、多步骤操作、需要参考资料）

## 🐛 问题与思考

### Q1: 什么样的经验适合沉淀成 Skill，而不是继续塞进主提示词？
**答**: 反复出现、有明确触发场景、步骤相对稳定、需要配套资源或脚本的经验适合做 Skill。偶尔一次的要求，放当前 Prompt 就够了。

### Q2: description 写得太泛或太窄，会分别带来什么问题？
**答**: 太泛会误触发，模型什么任务都想用；太窄会该用时不触发。好的描述要写清"做什么、什么时候用、什么时候不用"。

### Q3: Skill、Tool、Subagent 的边界怎样判断？
**答**: Skill 是可复用方法和资料，Tool 是可执行动作，Subagent 是有独立职责的执行角色。写 Skill 不等于增加一个新智能体，也不等于让模型获得新 API。

### Q4: 如果你要为代码审查写一个 Skill，正文里最应该写清哪些内容？
**答**: 要写清审查范围、优先级、输出格式、严重程度判断、不要做的事、需要查看的文件和可选脚本。Skill 要能指导稳定行为，而不是只写一句"请认真审查"。

## 📝 学习总结

### Skill
- Skill 的关键机制是渐进式加载：先看名称和描述，任务匹配后再读取完整 SKILL.md，真正需要时才读取资源或运行脚本。这样既节省上下文，也方便专业能力在不同 Agent 间复用。
