# 大模型微调基础

## 📅 学习信息
- **日期**: 2026-09-04
- **主题**: 大模型微调基础
- **目标**: 理解微调在大模型应用开发中的位置：它解决的不是"资料查询"，而是"让模型在固定任务上更稳定地按规则输出"。

## 📚 核心知识点

### 1. 微调的本质
- 大模型生成文本的基本方式是"根据上下文预测下一个 token"。微调通过提供训练样本（输入-输出对），调整模型的部分参数或 adapter 权重，让模型在类似输入场景下更倾向于生成你期望的输出。它改变的是模型的"行为习惯"，而不是给它塞入新知识。

### 2. 微调 vs Prompt vs RAG vs Agent
- **Prompt 工程**：把任务说清楚、约束格式、提供少量示例。适合快速验证和灵活调整。
- **RAG（检索增强生成）**：从外部知识库检索相关信息，拼接到 Prompt 中。适合私有资料、最新信息、可追溯来源的场景。
- **微调**：调整模型参数，让模型内化某种输出风格、格式或任务行为。适合长期稳定、高频重复、格式固定的任务。
- **Agent / Workflow**：编排多步流程、工具调用和条件判断。适合复杂业务流程。

### 3. Base Model vs Instruct Model
- **Base Model**：预训练后的原始模型，擅长续写，但不一定理解用户指令。适合继续预训练或特殊领域适配。
- **Instruct Model**：经过指令微调和对齐的模型，天然理解对话、指令和助手角色。绝大多数应用开发优先选择 Instruct Model。

### 4. 微调的典型适用场景
- 固定输出格式（如 JSON、特定模板）
- 统一语言风格（如客服话术、品牌语调）
- 专业术语习惯（如医疗、法律领域的表述方式）
- 小模型能力补强（让小模型在特定任务上接近大模型表现）
- **不适合**：频繁更新的知识、需要引用来源的信息、复杂业务流程

### 5. 关键概念
- **Token**：模型处理文本的最小单位，微调的本质是让模型更倾向于生成特定 token 序列。
- **Loss（损失）**：模型预测结果与标准答案之间的差距。训练的目标就是最小化 loss。
- **Adapter / LoRA**：不修改原模型参数，而是在模型旁边加一层小参数矩阵。训练快、显存占用小、可插拔。
- **过拟合**：模型把训练集"背下来了"，训练 loss 很低，但遇到新输入时效果差。
- **训练集 / 验证集**：训练集用于更新参数，验证集用于评估泛化能力。两者必须独立。
- **微调实验卡**：记录每次实验的目标、模型、数据、参数、基线对比和失败样例，便于追踪效果变化来源。

### 6. 重要机制
- **训练（Training）**：模型预测结果与标准答案比较，计算 loss，反向传播更新参数。
- **推理（Inference）**：使用训练好的参数，根据输入生成输出，参数不再变化。
- **评估（Evaluation）**：用验证集或真实业务输入测试模型效果，不能只看训练 loss。
- **参数高效微调（PEFT）**：如 LoRA、QLoRA，只训练少量参数，大幅降低显存和时间成本。

## 💻 示例

### 示例 1：微调数据格式（JSONL）
```jsonl
{"messages": [{"role": "user", "content": "请将以下文本总结为3句话"}, {"role": "assistant", "content": "总结结果..."}]}
{"messages": [{"role": "user", "content": "提取以下合同中的甲方和乙方"}, {"role": "assistant", "content": "甲方：XXX\n乙方：YYY"}]}
{"messages": [{"role": "user", "content": "将这段技术文档翻译成通俗语言"}, {"role": "assistant", "content": "用大白话解释..."}]}
```
- 每行一条训练样本，格式为 `{"messages": [...]}`
- 至少准备 50-100 条高质量样本，越多越好
- 样本要覆盖真实业务场景的各种情况

### 示例 2：微调 vs Prompt 对比
**同一个任务：将用户输入转换为 JSON 格式**

| 方式 | 实现 | 优点 | 缺点 |
|------|------|------|------|
| **Prompt** | 在 Prompt 中写"请将输入转换为 JSON，包含 name、age、city 字段" | 灵活，随时可改 | 每次消耗 Token，小模型可能不稳定 |
| **微调** | 用 100+ 条"输入→JSON"样本训练模型 | 稳定、快速、不消耗 Prompt Token | 格式变更需重新训练 |

### 示例 3：微调实验卡模板
```markdown
## 实验 #1：客服话术微调

### 目标
让模型在回复客户时，使用公司标准话术（开头问候、结尾感谢、避免敏感词）

### 模型
qwen2.5-7b-instruct

### 数据
- 训练集：200 条客服对话样本
- 验证集：30 条未参与训练的对话

### 训练参数
- 方法：LoRA
- 学习率：2e-4
- Epoch：3

### 基线对比
- 微调前：60% 符合话术规范
- 微调后：85% 符合话术规范

### 失败样例
1. 用户输入"我要投诉"时，模型没有先道歉，直接问原因
2. 长对话中，模型遗漏了结尾感谢语
```

## 🐛 问题与思考

### Q1: 为什么说微调不是"把资料塞进模型"？
**答**: 微调调整的是模型参数或 adapter 参数，让模型在类似输入下更倾向于生成某种输出；它不会在模型内部生成一个可检索、可更新、可引用来源的资料库。企业制度、产品手册、最新政策这类知识更新问题，通常优先考虑 RAG。

### Q2: 训练和推理最核心的区别是什么？
**答**: 推理只读取当前参数，根据输入生成输出，参数不会变化；训练会把预测结果和标准答案比较，计算 loss，并根据误差更新参数或 adapter。普通聊天不会自动微调模型。

### Q3: Base Model 和 Instruct Model 有什么区别？为什么应用场景通常优先选 Instruct Model？
**答**: Base Model 更像预训练后的续写器，不一定天然理解用户指令；Instruct Model 已经经过指令微调或对齐，更懂任务、对话和助手式回答。多数应用开发不是从零塑形模型，所以优先选 Instruct Model 更稳。

### Q4: Prompt 工程、RAG、微调、Agent / Workflow 分别适合解决什么问题？
**答**: Prompt 工程适合把任务说清楚、约束格式和提供示例；RAG 适合补充外部知识、私有资料和最新信息；微调适合长期稳定的格式、风格、标签、术语和行为习惯；Agent / Workflow 适合多步执行和工具调用。

### Q5: 训练 loss 下降但验证效果不好，可能有哪些原因？
**答**: 可能是过拟合、训练数据太少或太重复、验证集不代表真实场景，也可能是模型只学会训练集表面格式。判断效果时不能只看训练 loss，还要看验证 loss、人工样例和真实业务输入。

### Q6: 开始训练前为什么要先写"微调实验卡"？
**答**: 实验卡能记录任务目标、模型、数据、参数、基线、微调后效果和失败样例。没有这些记录，就很难判断效果变化来自数据、参数、模型还是评估样例。

### Q7: 如果企业知识库问答效果不好，你会先检查 RAG 还是先做微调？为什么？
**答**: 通常先检查 RAG。企业知识库问答多半是资料是否召回、内容是否新、引用是否准确的问题。微调可以改善表达习惯和任务行为，但不适合作为频繁更新知识的主要承载方式。

## 📝 学习总结

### 微调
- 大模型生成文本的基本方式，是根据上下文预测下一个 token。微调通过训练样本调整模型参数或 adapter，让模型在某些输入场景下更倾向于生成你希望的输出。它适合固定任务、稳定格式、统一风格、术语习惯和小模型能力补强，不适合承载频繁变化的知识，也不能替代业务流程。
